# Lead Bridge

## Обзор (1.12)

Администратор видит общие показатели, сравнение баеров и фильтр пользователя. Баер видит только свои показатели, график и топ связок; ограничение применяется в SQL на сервере. Период: сегодня, 7, 30 или 90 дней по личному часовому поясу. Отбор идёт по дате поступления лида, статусы — текущие для этой группы заявок.

График разделяет принятые ПП заявки, обработку и проверку. SENT не считается апрувом. Апрувы включают paid; процент апрува считается как approved+paid / (approved+paid+rejected+trash). При отсутствии решений показано тире. Рейтинги сортируются по числу лидов, апрувам или заявкам на проверке. Нет статуса означает отсутствие CRM-статуса, включая ещё не отправленные заявки. Финансовые показатели не рассчитываются. Под графиком доступна таблица значений; данные обновляются при открытии страницы. Apps Script менять не требуется.

## Автоматические статусы агентства (1.11)

Для Skylead/Cashfactories в режиме «Агентство» worker автоматически опрашивает `/ext/list.json` по внутренним ID `oid`, до 100 заявок за запрос. Постбэк ПП остаётся на Binom. В Apps Script менять ничего не нужно: прежний status polling получает обновлённый partner_status. Обновление в Sheets зависит от включённого триггера; события TikTok — от настроек Signal postback.

Проверяются только SENT-заявки с агентским snapshot. Старые SENT добавляются автоматически, новые регистрируются SQLite-триггером. Вебмастер и Lemonad продолжают работать через постбэки. Пакеты разделены по snapshot партнёрки и токену; смена текущих настроек не меняет принятые заявки. `uid` ответа — внутренний ID ПП, `id` — внешний extu; проверяются оба. Чужие, отсутствующие, неоднозначные и неизвестные статусы не применяются.

Период: 5 минут для ожидания/холда, 1 час после решения (проверки продолжаются для поздних исправлений). До одного пакета за 10 секунд между отправками; при большой очереди интервал может увеличиваться. Ошибки чтения повторяются с задержкой от 5 минут до часа, не меняют SENT и не повторяют отправку лида. wait→new, hold→hold, approve→approved, cancel→rejected, trash→trash. Правила защиты от регрессии общие с постбэком, свежий callback во время запроса имеет приоритет.

Карточка агентской ПП показывает режим и число ошибок; карточка лида — время последней проверки/успеха и ошибку. Для восстановления после смены токена старым заявкам потребуется отдельная процедура обновления учётных данных: snapshot не перезаписывается. Опрос использует тот же защищённый dispatch.lock и deploy.pause. Отдельный cron не нужен.

## Тип аккаунта ПП (1.10)

В карточке Skylead/Cashfactories выберите «Вебмастер» или «Агентство». Старые записи без этой настройки остаются вебмастерами. Для Lemonad выбор не используется. Это режим интеграции, он не меняет тип или права аккаунта в самой ПП.

Вебмастер: `/wm/push.json`, обязательны числовые offer и flow. Агентство: `/ext/add.json`, offer без flow; поле потока в связке скрывается. Базовые адреса Skylead `https://api.skylead.biz` и Cashfactories `https://cashfactories.com/api`. Агентский extu — стабильный SHA-256 от namespace баера и строкового TikTok Lead ID; exts — логин баера. Исходный TikTok Lead ID остаётся в uuid, подтверждённый clickid — в subid. IP и остальные метки передаются в обоих режимах. Ответ считается успешным только с status=ok и внутренним id; uid не заменяет id.

Тип можно менять для существующей записи: он применяется к новым заявкам всех её связок. Принятые заявки и ручные повторы используют исходный snapshot. После переключения агентства на вебмастера проверьте ID потока в каждой связке. Настройки Sheets и URL постбэка менять не требуется. API `/leads/add.json` скачанного лендинга этим выбором не подключается.

Документация агентства: [Skylead](https://my.skylead.biz/help/api.php#extadd), [Cashfactories](https://cashfactories.com/help/api.en.php#extadd).

TikTok Instant Forms → Google Sheets → очередь PHP → Binom v1/v2 → Lemonad. Обратный путь: Lemonad → мост → Sheets → TikTok Signal postback.

Панель: https://bridge.naturalsolution.help/. Доступ выдаёт администратор. Рабочие настройки, секреты и лиды в репозиторий не входят.

## Возможности

Баер видит только свои трекеры, партнёрки, связки и лиды. Администратор создаёт аккаунты, видит все записи и фильтрует журнал по пользователю. Один публичный action.php, настройки в браузере, зашифрованные данные SQLite вне web-root. Руководство доступно по кнопке «?».

Клик Binom подтверждается до вызова ПП. Заявки дедуплицируются по баеру и TikTok Lead ID, настройки сохраняются в неизменяемом snapshot. Неопределённые сетевые результаты требуют сверки, а не слепого повтора.

UI-даты: `18:12:21 18.09.2026`, по умолчанию Europe/Moscow. Каждый пользователь выбирает Europe/Moscow или UTC в Настройках. В базе и API время остаётся UTC. Три состояния сортировки: возрастание → убывание → исходный порядок. Журнал сортируется до пагинации. Иконки Lucide и подсказки доступны мышью и клавиатурой.

## Подключение баера

1. **Трекеры.** v1: API key из Settings → API. v2: API_KEY из Settings → Click API. Click URL — полный HTTPS URL без параметров; в v1 сохраняйте настоящее имя PHP-файла, в v2 обычно `/click`.
2. **Партнёрки.** Webmaster token из профиля Lemonad. Для всех связок аккаунта используйте одну запись партнёрки.
3. Скопируйте её URL постбэка в Lemonad → профиль → Global postback and API. Включите `new`, `approved`, `rejected`, `trash`, `paid`. Сохраните отдельный постбэк ПП → Binom: мост сам не регистрирует конверсии в трекере.
4. **Связки.** Выберите трекер/партнёрку, значение `key` из ссылки кампании и API `offerId` Lemonad. Проверьте точные Parameter в Traffic Source и активируйте связку. Номер Token используется для диагностики, отправку определяет Parameter.
5. Создайте Google-таблицу или отдельный лист для кампании. Обязательны `Lead ID` (или `TikTok Lead ID`) и `Phone`. Опциональны `Name`, `Campaign ID`, `Ad Group ID`, `Ad ID`, `Advertiser ID`, `Form ID`. ID и телефон должны поступать текстом, без округления.
6. Установите Apps Script из панели, сохраните, обновите таблицу. Выберите лист кампании; его JSON вставляется в **Lead Bridge → Настроить**, не в код. Выполните **Подготовить и проверить**.
7. Подключите TikTok Lead export. Удалите старые отправляющие триггеры, включая триггеры другого владельца. Включите один минутный `bridgeTick`.
8. Signal postback: Lead status → `TikTok Lead Status`, TikTok lead ID → исходный TikTok ID. Настройте события в Events Manager. Binom Click ID не является TikTok Click ID.

После обновления Apps Script проверьте «Подключённые листы» и выполните «Подготовить и проверить» для каждого подключённого листа. Работающий триггер сохраняется. Для старых статусов нужен повтор постбэка из ПП, не повтор лида.

## Статусы и ограничения

| Значение | Значение |
|---|---|
| QUEUED | Заявка сохранена в очередь |
| SENT | ПП подтвердила приём, не апрув |
| REVIEW | Нужна сверка внешнего результата |
| RETRY | Проверить прежний Lead ID / квитанцию |
| TikTok Lead Status | Статус из постбэка ПП |
| Partner Status Updated | Время принятого изменения статуса |

CRM-статус не выводится из SENT. Поздний new не отменяет решение; paid окончателен. Для approved/rejected/trash действует порядок получения: шаблон не содержит времени события. Повтор текущего статуса ничего не меняет. Неоднозначный clickid сохраняется для проверки.

Глобальная ссылка относится к одной записи партнёрки. Две записи с одинаковыми API-реквизитами не объединяются автоматически. Поиск использует snapshot.route.partner, поэтому изменение связки не нарушает старые лиды. Посторонние лиды игнорируются. Старые per-route ссылки поддерживаются. Sheets опрашивает до 100 сохранённых квитанций на лист за запуск, включая SENT, без повторной отправки.

```bash

bash scripts/check.sh
```

Тестируется собранный артефакт во временных каталогах: v1/v2, дедупликация, сетевые ошибки, изоляция баеров, CSRF, постбэки, точность ID, Sheets и сортировка. Внешние ПП/трекеры не вызываются. dist не коммитится.

## Сервер

Web-root `/var/www/lead-bridge/`, исполняемый файл action.php. Приватный каталог `/var/lib/lead-bridge/`; bridge.sqlite и master.key нужны вместе для восстановления. Отдельный FPM-пул leadbridge, сокет `/run/php/leadbridge.sock`. Worker: lead-bridge.service, CLI `action.php worker`. Бэкапы: lead-bridge-backup.service / .timer, `/var/backups/lead-bridge`. Health: `GET /?health=1`.

Nginx: `/etc/nginx/sites-available/lead-bridge`. privacy.html обслуживается отдельным location и не меняется при релизе. Для новой установки подготовьте каталог и права, выполните CLI init с BRIDGE_DATA, BRIDGE_URL, BRIDGE_ADMIN_PASSWORD через защищённое окружение, настройте HTTPS, FPM и systemd. Приёмник релиза рассчитан на подготовленный сервер.

## CI/CD

PR запускает сборку и тесты. Push main после проверок деплоится в environment production. Ручной workflow доступен для main. Внешние PR не получают секреты.

Секреты production: DEPLOY_HOST, проверенный DEPLOY_KNOWN_HOSTS и отдельный DEPLOY_SSH_KEY пользователя leadbridge-deploy. Environment ограничен веткой main. SSH-ключ имеет forced command `sudo -n /usr/local/sbin/lead-bridge-deploy`; forwarding, PTY и произвольные команды запрещены. Sudo разрешает только root-owned приёмник. В `/etc/lead-bridge-health-url` хранится публичный HTTPS-адрес панели.

Ограничения учётной записи дополнительно закреплены в `deploy/sshd-leadbridge.conf`: администратор устанавливает его как `/etc/ssh/sshd_config.d/60-leadbridge-deploy.conf` (root:root 0644), выполняет `sshd -t` и только после успешной проверки перезагружает конфигурацию SSH. Файл применяется только к leadbridge-deploy: обязательная команда приёмника, запрет пароля, forwarding, PTY и пользовательского SSH rc. Проверьте эффективные параметры через `sshd -T -C user=leadbridge-deploy,host=localhost,addr=127.0.0.1`; основной sshd_config должен подключать этот каталог.

Домашний каталог `/home/leadbridge-deploy` и `.ssh` принадлежат root:leadbridge-deploy с режимом 0750; `authorized_keys` — root:leadbridge-deploy 0640. У пользователя деплоя нет права заменять каталог или изменять ключи. Перед изменением прав проверьте, что пути не являются символическими ссылками, а файл ключей имеет одну жёсткую ссылку. Эти настройки устанавливаются администратором отдельно от CI; права и ключи других проектов не меняются.

Деплой получает только PHP по stdin, проверяет синтаксис, делает бэкап, ставит очередь на паузу и ждёт dispatch.lock. Затем атомарно заменяет файл, перезагружает FPM, запускает worker и проверяет SHA256/health. При ошибке возвращается предыдущий PHP. База автоматически не откатывается; миграции должны быть добавочными и совместимыми. Сам приёмник обновляется отдельно администратором.

Скачиваемый/копируемый Apps Script обновляется вместе с сервером, существующие таблицы обновляются вручную. Деплой не меняет настройки рекламы, ПП и TikTok.

### Защита блокировок деплоя

`/var/lib/lead-bridge-control` принадлежит root:root, режим 0755; `dispatch.lock` и `deploy.lock` — обычные файлы root:root 0644 с одной жёсткой ссылкой. Worker получает `BRIDGE_CONTROL=/var/lib/lead-bridge-control` через systemd и открывает блокировку только для чтения. В тестах без этой переменной используется временный BRIDGE_DATA.

Приёмник проверяет владельца/права каталогов, тип и количество ссылок файлов, открывает блокировки без усечения, создаёт pause с noclobber. Root не открывает и не меняет файлы управления внутри BRIDGE_DATA. Защищённый родитель исключает подмену между проверкой и открытием. Sudo разрешает приёмник только без аргументов. При развёртывании новой установки эти каталог, файлы и переменная worker обязательны; обновление старой установки требует безопасного завершения текущей обработки перед переключением блокировки.

`scripts/deploy_security_test.py` проверяет отказ при символических/жёстких ссылках и небезопасных правах. Сам приёмник устанавливается администратором отдельно; CI обновляет только приложение.

## Дополнительные рекламные метки (1.5)

Обновите Apps Script из панели и выполните «Подготовить и проверить». Дополнительные колонки: Placement, Campaign Name, Ad Group Name, Ad Name, ADID_V2, ADID_V2_NAME. Поддерживаются написания CAMPAIGN_ID, CAMPAIGN_NAME, AID_NAME (Ad Group Name), CID_NAME (Ad Name), Adset ID/Name; конфликтующие непустые значения останавливают строку с REVIEW. ADID_V2 и ADID_V2_NAME самостоятельны: из Ad ID/Ad Name не копируются. ID храните текстом. Пустые колонки не создают данные: источник должен записать значения в Sheets.

Сопоставление Binom чувствительно к регистру: `campaign_id` и `CAMPAIGN_ID` различаются. Для новых полей укажите точный Parameter в связке. Старые сопоставления не меняются автоматически. В карточке лида доступны все принятые метки.

В связке доступен режим меток Lemonad: прежний (Campaign ID / Ad ID), основные ID (ещё группа в utm_term и логин в utm_medium), все метки (дополнительные поля одним JSON-текстом в utm_term). API Lemonad документирует UTM, а не произвольные поля: https://docs.limonad.com/doc/public-api . Отображение/лимиты utm_term требуют сверки с ПП; приём лида сам по себе не подтверждает сохранение каждого поля. Старые snapshots и ранее отправленные лиды не переписываются и повторно не отправляются.

## Несколько кампаний в одной таблице (1.6)

Для каждой кампании Binom создайте свою связку с её ключом кампании; оффер и партнёрка могут совпадать. В одной Google-таблице создайте по листу на кампанию. Apps Script устанавливается один раз, минутный триггер `bridgeTick` один на все листы.

1. Создайте новый лист с шапкой или дублируйте пустой шаблон. Не копируйте строки лидов, квитанции и статусы.
2. Выберите этот лист → **Lead Bridge → Настроить** → JSON его связки → **Подготовить и проверить**.
3. В TikTok Lead export направьте форму в соответствующий лист; для обратных статусов настройте Signal postback для этого листа.
4. Проверьте назначения через **Lead Bridge → Подключённые листы**. Новый триггер создавать не нужно.

Настройки привязаны к неизменяемому ID листа, поэтому переименование/перемещение безопасны, а копия листа требует отдельного подключения. Лист без настройки пропускается. Лист с историей нельзя переключить на другой маршрут/сервер: создайте новый пустой лист. Обновить секрет той же связки можно. Дедупликация по баеру и TikTok Lead ID остаётся общей: копирование лида на другой лист не создаёт нового лида в другой кампании.

При обновлении с 1.5 прежний общий JSON один раз переносится только на листы с сохранёнными курсорами обработки (`cursor_<sheetId>` или `partner_cursor_<sheetId>`). Листы без истории запусков требуют явного подключения. Старые Script Properties сохранены, но после миграции не используются как настройка по умолчанию для новых листов. Существующие лиды и квитанции не переписываются.

Один запуск обрабатывает до 25 строк отправки/проверки и до 100 квитанций статусов на лист. Очерёдность строк и первого листа меняется, чтобы очередь одного листа не блокировала остальные. Общий бюджет — 220 секунд между запросами; ошибка одного листа записывается в журнал Apps Script и не останавливает другие листы. Это не снимает общие квоты Google Apps Script. Общую таблицу используйте внутри одной доверенной команды: редакторы её Apps Script имеют доступ к настройкам всех листов.

## Сессии панели (1.6.1)

Вход сохраняется на 30 дней бездействия и продлевается при работе с панелью, включая перезапуск браузера. Cookie: Secure, HttpOnly, SameSite=Strict. PHP хранит сессии в `BRIDGE_DATA/sessions` (0700), отдельно от общего каталога PHP с коротким сроком очистки; срок хранения соответствует сроку входа. Файлы создаёт пользователь приложения, без root. Выход удаляет серверную сессию и cookie. Смена/сброс пароля и блокировка аккаунта продолжают отзывать сессии через epoch (при самостоятельной смене пароля текущая сессия сохраняется). При переходе со старой версии потребуется один раз войти заново, так как каталог сессий изменился. Копировать старые файлы сессий не нужно; при восстановлении бэкапа каталог sessions можно не восстанавливать.

## Уведомление об обновлении Apps Script (1.6.2)

Администратор открывает **Настройки → Обновление Apps Script → Уведомить об обновлении Apps Script**. Публикация ручная: сам деплой уведомления не включает. Пользователи видят карточку справа сверху при следующем входе или загрузке страницы, со ссылкой на раздел «Подключение». Она просит заменить скрипт во всех действующих таблицах; один скрипт обслуживает все листы одной таблицы.

«Понятно» скрывает только эту публикацию для текущего пользователя, на всех его устройствах; это подтверждение прочтения, а не проверка обновления таблиц. Следующая публикация отображается заново. «Предпросмотр» показывает карточку только администратору без рассылки, «Снять уведомление» отключает её для всех при следующей загрузке страницы. Проверки прав и CSRF выполняются сервером, публикация/снятие записываются в журнал действий.

## Форматы обратного постбэка (1.7)

В карточке партнёрки в блоке «Статусы ПП → таблица → TikTok» выбираются Lemonad, Skylead или Cashfactories. Выбор сохраняется для этой записи партнёрки и меняет URL/инструкцию. Доступ проверяется по владельцу. Старые URL и ключи Lemonad остаются действительными; snapshot и отправка лидов не меняются.

Skylead/Cashfactories: `clickid={subid}&status={stage}&leadid={id}`, stage wait → new, hold → hold, approve → approved, cancel → rejected, trash → trash. Запоздалые wait/hold не отменяют решение. В исходном subid должен быть clickid Binom; поиск дополнительно ограничен аккаунтом ПП из snapshot. Сторонние лиды игнорируются. Apps Script передаёт hold как отдельный CRM-статус; не считайте его апрувом при настройке TikTok.

[Документация Skylead](https://my.skylead.biz/help/wm.php#postback): постбэк потока имеет приоритет над глобальным. Нельзя просто заменить существующий URL Binom ссылкой моста и ожидать конверсий в Binom: мост их не пересылает. Для двух получателей требуется поддержка отдельных адресов на стороне ПП или отдельная реализация доставки. Cashfactories использует общий формат по подтверждению пользователя.

В версии 1.7 была добавлена поддержка входящих статусов; исходящая отправка добавлена в 1.8 (ниже). Для этого изменения Apps Script обновлять не требуется, если уже установлена текущая версия с опросом статусов.


## Отправка Skylead / Cashfactories (1.8)

Создайте отдельный аккаунт в «Партнёрки», выберите сеть и вставьте API-токен из её профиля. Тип существующего аккаунта нельзя менять: создайте новый, чтобы не перепутать токены и действующие связки. Пустой токен при редактировании сохраняет текущий. Адрес API фиксирован: Skylead — https://api.skylead.biz/wm/push.json, Cashfactories — https://cashfactories.com/api/wm/push.json. Отправка JSON POST, токен в параметре id. Менеджер ПП должен включить доступ к отправке по API.

В связке выберите эту партнёрку, укажите числовые API ID оффера и потока (flow), страну ISO (например ZA), при необходимости валюту (ZAR). Для Lemonad прежние настройки работают без изменений. Конфигурация фиксируется в snapshot заявки.

Обе ПП требуют **IP покупателя**. Новый Apps Script передаёт колонку `Client IP` (также `IP Address`/`IP`). Обновите скрипт в таблицах, где нужен этот столбец. Если исходная Instant Form не даёт IP, сначала согласуйте с менеджером ПП способ приёма такого трафика. В стандартном режиме без публичного клиентского адреса новая заявка отклоняется до создания клика/вызова ПП. Согласованный с ПП режим генерации описан ниже. После исправления непринятой строки можно повторить её отправку.

Метаданные: campaign_id → utm_campaign, ad_id → utm_content, adgroup_id → utm_term, логин баера → utm_medium, источник tiktok → utm_source. Подтверждённый clickid Binom → subid, TikTok Lead ID → uuid. campaign_name/adgroup_name/ad_name/adid_v2/adid_v2_name → sub1/sub2/sub3/sub4/sub5. Эти sub-поля не показываются в статистике ПП по документации. Лимит 255 символов проверяется без обрезки. Остальные метки остаются в мосте/Binom, они не автоматически превращаются в поля ПП.

Успех: HTTP 2xx без транспортной ошибки, JSON status=ok и положительный целочисленный id (сохраняется строкой). duplicate, пустой ответ, таймаут и HTTP 200 без подтверждения — REVIEW без автоматического повтора. SENT не означает апрув; статусы идут существующим постбэком аккаунта. Формат обратной ссылки новой партнёрки выбирается по её типу, его также можно изменить отдельно.

Документация: [Skylead](https://my.skylead.biz/help/api.php#push), [Cashfactories](https://cashfactories.com/help/api.en.php#push). Адаптеры проверены заглушками; реальные заявки и включение API аккаунта требуют отдельной проверки владельцем.


## Временный IP для Instant Forms (1.9)

После подтверждения менеджера ПП доступен режим связки **IP для партнёрки → Случайный IP страны, если реального нет**. Работает только для Skylead/Cashfactories. Выберите страну и сохраните связку. По умолчанию остаётся реальный IP. Режим не включается автоматически в существующих связках.

Реальный `Client IP` имеет приоритет; некорректный переданный адрес не заменяется генерацией. При отсутствии IP мост один раз выбирает случайный публичный IPv4 из сохранённых диапазонов страны. Адрес, источник `generated`, страна и версия геобазы хранятся в зашифрованном snapshot и видны в карточке лида в `partner_ip`. Входные данные и fingerprint не меняются. Повтор того же лида и ручная сверка не меняют IP; смена страны/режима связки влияет только на новые заявки. Старые snapshots не переписываются. IP отправляется только в ПП, не подменяет IP посетителя в Binom. Автоматических повторов отправки нет.

Геоданные: [DB-IP IP to Country Lite](https://db-ip.com/db/download/ip-to-country-lite), CC BY 4.0, лицензия `central/DBIP-LICENSE`. В `central/ip-country.json` сохранена детерминированная выборка до 128 публичных диапазонов каждой страны из CSV (зеркало sapics/ip-location-db); точный URL, дата и SHA256 исходника записаны в файле. Это изменённая выборка, а не полная база. Геолокация разных баз может отличаться; соответствие геобазе самой ПП не гарантируется. `build.py` встраивает сжатые данные в action.php, внешних загрузок при приёме лида нет. Обновление диапазонов — отдельный проверенный релиз. Apps Script для режима генерации менять не требуется.


## Форма связки (1.9.1)

Первым выбирается аккаунт ПП. Для Lemonad показывается режим меток; для Skylead/Cashfactories — обязательный ID потока, режим IP, страна и валюта. Скрытые группы отключены и не отправляются формой. Выбор генерации делает страну обязательной. Сервер повторно проверяет тип ПП и обязательные поля; интерфейс не заменяет проверку прав владельца.


## Дублирование связок (1.9.2)

В списке связок иконка Lucide Copy слева от шестерёнки создаёт копию и открывает её настройки. Название получает copy1, copy2 и далее; копирование копии продолжает нумерацию исходного названия в рамках владельца. Сохраняются все настройки, включая активность, режим IP, токены и namespace дедупликации. ID и секрет выдаются новые, лиды не копируются. Для отдельной кампании измените её ключ и подключите новый лист JSON копии. Создание защищено CSRF и проверкой владельца; нумерация и запись выполняются в одной транзакции.
