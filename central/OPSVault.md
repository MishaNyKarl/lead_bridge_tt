# OpsVault: подключение Lead Bridge

Код поддерживает протокол OpsVault 0.1.2. Настройки доступны в панели, руководство — по кнопке «?». Сервер сохраняет прежние users.id, логины, hashes и владельцев entities/leads. Миграция только добавляет `sso_links`, `sso_attempts` и `sso_reservations`. Настройки новой установки: gate/JIT выключены до доставки клиента и секретов; для рабочего сервиса JIT включается оператором по поручению владельца.

## Регистрация оператором OpsVault

Предлагаемые параметры: service slug/client ID `lead-bridge`, название `Lead Bridge`, issuer `https://portalwiki.world/sso`, scope `openid profile`.

- Callback: `https://bridge.naturalsolution.help/?opsvault=callback` (точное совпадение).
- После выхода: `https://bridge.naturalsolution.help/`.
- Ссылка входа на карточке сервиса: `https://bridge.naturalsolution.help/?opsvault=login`.
- Пилот и точные пары пользователей хранятся только в приватной заявке оператору; публичный репозиторий не содержит реальных логинов.

Оператор задаёт новый случайный `SSO_REGISTER_CLIENT_ID=lead-bridge` и новый `SSO_REGISTER_CLIENT_SECRET` через защищённое окружение, затем выполняет в существующем OpsVault:

```sh
python manage.py sso_register_service lead-bridge --name 'Lead Bridge' \
  --redirect-uri 'https://bridge.naturalsolution.help/?opsvault=callback' \
  --post-logout-uri 'https://bridge.naturalsolution.help/'
python manage.py sso_grant EXACT_USERNAME lead-bridge --role admin
```

Для фоновой отправки/опроса Sheets и ПП нужен отдельный `--allow-import`, только если оператор явно разрешил его пользователю. Общий logout не отзывает это фоновое разрешение; block/revoke grant запрещает его. Обычный клиент не может сам зарегистрировать сервис или выдать grant.

## Серверные секреты и публикация

До включения gate установите только для backend PHP-FPM и worker:

- `BRIDGE_SSO_CLIENT_SECRET`: новый confidential secret клиента, минимум 32 символа.
- `BRIDGE_SSO_ENCRYPTION_KEY`: base64 от отдельных случайных 32 байт. Постоянный ключ для attempts/pending/leases; не master.key и не ключи провайдера.
- `BRIDGE_SSO_EMERGENCY_IDS`: локальные ID несвязанных аварийных аккаунтов через запятую, по умолчанию `admin`. Связанный аккаунт никогда не получает этот обход. Сохраняйте отдельного несвязанного администратора перед пилотом.

Доставка секретов — защищённым операторским каналом, server-only файл 0600/secret manager. Не в Git, браузер, argv, логи или чат. FPM обычно очищает окружение: оператор должен явно передать эти переменные в отдельный пул leadbridge; worker получает то же окружение. Перезапуск пула/worker выполняется штатно после настройки. Не трогайте другие сайты или RSA/Fernet/VAULT_KEY OpsVault.

Штатный первоначальный setup: `python3 deploy/configure-opsvault.py` от администратора сервера; JSON подаётся на stdin через защищённый канал (не аргументом). Поля: client_id/client_secret/encryption_key, recovery_id/recovery_login/recovery_password и список reservations с local_user_id/local_login/subject. Клиент и Identity должны быть зарегистрированы оператором заранее. Setup проверяет защищённые пути/файлы без ссылок, удерживает защищённые deploy/dispatch locks, создаёт бэкап, атомарно настраивает только пул/worker/лог сайта Lead Bridge; запросы БД выполняет как leadbridge. Сохраняет прежние IDs/hashes/epochs/owners и создаёт отдельный аварийный аккаунт. Повтор не ротирует секреты. При ошибке настройки возвращаются прежние конфиги; уже добавленная схема/успешно завершённая транзакция БД автоматически не откатываются. После setup используйте обычный приёмник PHP-релиза; он делает паузу, атомарную замену, restart и health-check.

Сначала бэкап SQLite вместе с master.key, затем штатный деплой единственного `central/dist/action.php`. Для новой конфигурации отдельно сохраните SSO encryption key. Откат PHP не откатывает БД. Зависимости OIDC уже включены в сборку; Composer на production не нужен.

**До реального OIDC-входа оператор обязан исключить query callback из access/error/proxy/APM логов.** Для Nginx используйте logging format с `$uri` вместо `$request`/`$request_uri` на auth callback (query содержит code/state). Не логировать Authorization, Cookie, POST body, ответы credentials API. Приложение отдаёт no-store/no-referrer. Изменение журналирования применяет оператор только для этого сайта с `nginx -t`; код сам Nginx не меняет.

## Настройка и связь

1. Аварийный администратор открывает Настройки → Подключение OpsVault, задаёт client ID и whitelist **локальных ID**, затем включает вход. ID аккаунта показан в форме редактирования и ссылке `edit_user`; логин OpsVault не является локальным ID. JIT пока не включать. Связь локального администратора запрещена, пока нет другого активного несвязанного аварийного администратора, выбранного через серверное окружение. Этот контроль повторяется перед подтверждением.
2. Существующий пользователь из whitelist входит по текущему отдельному паролю. До связи он видит только Настройки для связывания, без доступа к данным или обычным изменениям.
3. «Связать OpsVault»: повторный ввод текущего пароля, явное согласие на vault. Перенаправление в OpsVault использует его сессию в этом браузере.
4. Возврат показывает локальный аккаунт и подтверждённую идентичность OpsVault. Пользователь подтверждает оба аккаунта POST. Pending/password/lease зашифрованы серверно, TTL не более 300 секунд. Callback атомарно одноразовый и привязан к отдельной Secure/HttpOnly/Lax cookie; основная cookie панели остаётся Strict.
5. Свежий grant и сохранение credentials должны успешно завершиться **до** локального commit. Логин/hash/ID владельцев неизменны. Epoch отзывает все прежние локальные/OIDC/local-linked сессии. Новая OIDC-сессия выдаётся с новым ID.
6. После связи роль `user` означает баера, `admin` — администратора; локальное users.role не выдаёт центральные права. Owner scope продолжает действовать на сервере. Пароль/роль связанного аккаунта нельзя менять отдельно в панели. Карточка пароля — в штатном хранилище OpsVault.

JIT создаёт аккаунт при первом разрешённом входе OpsVault, если для issuer+subject нет прежней связи или резерва. Выдаёт отдельные случайные логин/пароль/ID и сохраняет пароль в vault до commit; имя используется только для отображения. Повторный вход возвращает тот же локальный аккаунт. Read восстанавливает canonical credentials после publish+rollback. Коллизия существующего ID/логина закрывает операцию: автоматического слияния нет. API409 не вызывает автоматический повтор публикации. При конфликте оператор сверяет binding.

Для существующих пользователей оператор получает точные UUID Identity в OpsVault и создаёт `sso_reservations` с прежними local ID (в браузере: Настройки → Существующие аккаунты). Это не связывание и не выдача доступа к данным: зарезервированный subject видит предложение подтвердить прежний аккаунт, JIT не создаёт ему дубликат. Подтверждение проверяет резерв в той же транзакции; связь с другим локальным аккаунтом запрещена. Имя/email/похожий логин не заменяют UUID. Ошибочный резерв можно снять в браузере до подтверждения связи.

Оба типа связанных сессий проверяют активность, точную связь и grant; read cache не более 60 секунд от начала проверки, POST — свежая проверка, длительные действия — повтор перед commit. Gate off закрывает связанные аккаунты, в том числе парольный вход. 401/403 закрывает сессию; outage/invalid response после TTL даёт 503. Локальный выход закрывает мост; общий OIDC logout закрывает семейство и исходную сессию портала на этом устройстве. Для local-linked общего выхода нет.

При фоновой отправке разрешение проверяется до каждого внешнего этапа и после ответа. Отзыв в процессе HTTP не отменяет уже отправленный запрос: заявка переходит на сверку, без повторной отправки. До первого внешнего запроса отсутствие разрешения сохраняет очередь. Опрос статусов не enqueue/send SENT заново. Для связанных владельцев Sheets API также требует фоновый grant.

## Проверки и живая приёмка

`bash scripts/check.sh` проверяет собранный артефакт, временные БД и заглушки. Сфокусированные SSO-тесты включают реальную подпись RS256/JWKS с временным тестовым ключом, PKCE, mandatory claims, неправильные подписи/issuer/aud/nonce/sid, cache/revoke/роль/gate/outage, публикацию/rollback/recovery/коллизии. Проверка UI выполняется локально в браузере, включая клавиатуру и узкий экран. Реальные лиды, клики и конверсии не нужны.

После регистрации, доставки секретов и штатного деплоя подтвердите реальным пилотом: существующая portal-сессия → link → тот же local ID и owner counts; повторный вход и парольный вход; отзыв grant и смена роли; чужие записи; карточку реквизитов; local/global logout; отсутствие секретов в журналах. До этих действий production-вход не считается подтверждённым.

## Зависимости

OIDC: `jumbojett/openid-connect-php` 1.0.2; RSA: `phpseclib/phpseclib` 3.0.57; transitive версии и commit refs в `oidc-composer.lock`. Composer audit при установке не нашёл известных advisories. Исходники и лицензии находятся в `oidc-vendor/`; `oidc-vendor-sha256.json` проверяется build.py до включения библиотек в один PHP. Код библиотек не изменён. При обновлении повторить Composer audit, скопировать проверенные исходники `scripts/vendor_oidc.py`, прогнать негативные тесты. При первом SSO-запросе пользователь приложения сохраняет встроенную ZIP-библиотеку в `BRIDGE_DATA/oidc-library` (0700, файл 0600); PHP `phar://` читает её без распаковки. Проверяется SHA256 архива из сборки, символическая ссылка не принимается. Нужны штатные PHP Phar/zlib/openssl/curl/sodium/pdo_sqlite; новые пакеты production не загружаются.
